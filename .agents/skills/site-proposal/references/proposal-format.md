# 改善提案書の形式

保存先：評価結果と同じ `reports/sites/<ドメイン>/<YYYY-MM-DD>/`

| ファイル | 内容 |
| --- | --- |
| decision.json | decide.py の判定結果（作成しない場合も保存） |
| proposal.md | 人が読む提案書（運営・営業ユーザー・企業向け） |
| proposal.json | アプリに取り込める構造化データ |

## 構成の考え方

一般的なサイト改善提案書の構成（概要 → 背景 → 現状と課題 → 施策 → 目標 → 予算・スケジュール → 事例）に沿う。
ただし SiteOffer は企業のアクセス解析を見られないため、次のように置き換える。

| 一般的な提案書 | SiteOffer での扱い |
| --- | --- |
| アクセス数・CV数の現状 | 外から観測できる事実（導線、表示、情報量）と評価点 |
| 数値目標（問い合わせ◯%増） | 観測できる改善目標（再評価での項目レベル）と、公開後に測る指標の候補。増加は約束しない |
| 費用対効果 | 価格は運営の設定値。未設定なら「未設定」。効果を金額で示さない |
| 他社事例 | 実際に確認した同地域・同業サイトの良い点だけ。確認していない事例・数字は書かない |
| 1スライド1メッセージ・平易な言葉 | 1施策1テーマ。専門用語は避け、使う場合は一言で説明 |

## 優先度の付け方

施策ごとに影響度と工数を付け、組み合わせで優先度を決める。

- **影響度**：サイトの目的（主に問い合わせ）への影響。高＝連絡・理解を直接妨げる（A1, A2, B1, D1 の低レベル、致命項目）。中＝判断や信頼を弱める（B2, B3, C系, D2）。低＝目に見えにくい技術的な欠け（F, G, E の一部）。
- **工数**：小＝文言・配置・設定の変更。中＝セクション追加や素材の準備が必要。大＝構成の作り直し、企業側の情報収集が多い。
- **優先度**：高＝影響度高（工数を問わない）または影響度中×工数小。中＝影響度中×工数中・大、影響度低×工数小。低＝それ以外。

## サイト構成の提案

- 単一ページを既定値にしない。会社情報、サービス詳細、実績、保証、採用、公表資料などに固有の目的と十分な本文がある場合は、目的別ページとして提案する。
- トップは全情報の置き場ではなく、会社・主要サービス・信頼材料・主要行動を示し、詳細ページへ案内する入口とする。
- 本文を取得できていないリンク先がある場合は、ページ数を断定しない。「リンク先本文を取得・確認してから、統合または独立ページを決める」と書く。
- 単一ページは、単一サービスや短いキャンペーンなど、訪問者の判断に必要な情報を削らず完結できる場合に限る。
- `proposal.json.actions[].change.spec` に、採用する構成と案件固有の理由を書く。SEOに有利そう、テンプレートだから、ページ数を増やしたい、だけを理由にしない。

## proposal.md

```markdown
# Webサイト改善提案書：<企業名>

> この資料は SiteOffer が公開情報をもとに作成した**非公式の改善提案**です。<企業名>様の公式な資料ではありません。

| 項目 | 値 |
| --- | --- |
| 対象サイト | URL |
| 評価日 / 提案作成日 | … |
| 総合点 | NN / 100（判定：閾値 NN 未満 / 致命項目 …） |
| 根拠 | evaluation.md（同ディレクトリ） |
| 提案版 | v1 |

## 1. 概要
- 現状を一言で：…
- 優先して直したい点（最大3つ）：…
- 提案の方向：…
- 期待できること：「訪問者が◯◯しやすくなる」の形で。売上・問い合わせ・順位の増加は書かない。

## 2. 背景と目的
サイトの目的と想定顧客（推定であることと根拠）。今の状態が、その目的に対してどこで妨げになっているか。

## 3. 現状と課題
評価の点数表（カテゴリ別）。
課題一覧の表：| 課題ID | 内容 | 該当項目 | 影響度 | 根拠（URL・場所） |
良い点（維持するもの）も短く書く。

## 4. 改善施策
施策ごとに次の表と説明を書く。

### P-01 <施策名>

| 項目 | 内容 |
| --- | --- |
| 優先度 | 高（影響度：高 / 工数：小） |
| 対応する課題 | I-01（A1, A2） |
| 対象箇所 | https://…/ のヘッダー、スマホ表示の画面下部 |
| 現状 | 観測した事実。評価の observations と一致させる |
| 問題点 | 訪問者にとって何が困るか |
| 改善内容 | 何をどう変えるか。配置、文言、仕様（サイズ・色・項目数など） |
| 範囲 | 範囲内 / 要確認 / 範囲外（運営へ相談） |
| 企業への確認事項 | 受付時間、無料対応の有無など |
| 確認方法 | 改善後に何を見れば達成と言えるか |

改善後のイメージ（文言案・構成案）：
（テキストのワイヤーフレームや、見出し・ボタン文言の案。企業の事実に関わる部分は【要確認：…】と書く）

## 5. 実施の順番
優先度の表と、実施順（第1段階：すぐ直せる高優先 → 第2段階：素材が必要なもの → 範囲外・運営相談）。

## 6. 改善後の目標と確認方法
| 目標 | 現状 | 改善後の目標 | 確認方法 |
評価項目のレベル（例：A1 レベル1→3）や総合点の再評価を目標にする。
公開後に測れる指標の候補（電話タップ数、フォーム送信数など）は、企業の同意と計測設定が必要と書く。数値の増加は約束しない。

## 7. 提供範囲・費用・スケジュール
商品、価格、継続費用、納期は運営の設定値を書く。未設定なら「未設定（運営が決定）」。
範囲外の要望は運営へ相談と明記。制作の流れ：情報・素材の確認 → 制作 → 運営確認 → 企業確認 → 公開。

## 8. 参考比較（任意）
実際に確認した同地域・同業サイトの良い点と、そのURL・確認日。確認していなければこの章を省く。

## 9. 営業向けの要点（企業には渡さない）
- 電話で最初に伝える3点（観測事実に基づく、短い言葉）
- 想定される質問と答え方
- 運営に引き継ぐべき事項

## 10. 注意事項・未確認事項
推測を含む箇所、企業に確認が必要な情報、評価できなかった項目、素材の利用権。
```

9章は営業ユーザー用。企業へ共有する版を作るときは9章を除く。
