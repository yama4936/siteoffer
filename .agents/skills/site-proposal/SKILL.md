# 改善提案書（site-proposal）

評価で改善が必要と判定されたサイトについて、運営・営業ユーザー・企業が読める改善提案書を作る。
提案書は営業ユーザーが電話・商談で使い、契約後は制作の指示にもなる。だから「どこを・どのように」を、制作者がそのまま作業できる粒度で書く。

## 前提として守ること

- **評価の根拠から外れない。** 課題と施策は evaluation.json の observations に結び付ける。評価にない問題を新たに足すなら、確認した URL と事実を書き、evaluation にも追記する。
- **企業の事実を作らない。** 料金・実績・資格・受賞・お客様の声・受付時間・「無料」などは、サイトで確認できたものだけ使う。それ以外の文言案には【要確認：…】を付ける（REQUIREMENTS.md §10.2）。
- **効果を約束しない。** 売上・問い合わせ・検索順位が増えるとは書かない。「訪問者が◯◯しやすくなる」まで。
- **非公式の提案であると明記する**（REQUIREMENTS.md §11）。
- **価格・報酬・範囲を勝手に決めない。** 商品・価格・納期は運営の設定値。未設定なら「未設定」。
- **提案書を作るかは閾値で決める。** 閾値が未設定のあいだは自動で作らない。

## 手順

`<skill>` はこのスキルのディレクトリ（`.agents/skills/site-proposal`）。`$OUT` は評価結果のディレクトリ。

### 1. 評価結果の確認

`$OUT/evaluation.json` に `summary` があることを確認する。なければ site-evaluation スキルを先に実行する。

### 2. 作成可否の判定

```bash
python3 <skill>/scripts/decide.py $OUT/evaluation.json > $OUT/decision.json
```

| decision | 対応 |
| --- | --- |
| create | 手順3へ進む |
| skip | 提案書は作らない。総合点と閾値をユーザーに伝えて終える |
| pending | 提案書は作らない。理由（閾値未設定、カバー率不足、評価不能）を伝える。閾値未設定なら、その場で使う閾値を決めてもらうよう選択肢で確認する |

- ユーザーがその場で閾値を明示した場合だけ `--threshold <値>` を付けて再判定する。この値は設定ファイルに書き込まない。恒久的な値にするかは別に確認する。
- 閾値の値を自分で決めない。閾値はユーザーが判断する未決事項（config/site-evaluation.json）。

### 3. 材料を読む

- `$OUT/evaluation.json` と `evaluation.md`：課題・根拠・強み・サイトの目的。
- `$OUT/collected.json` とスクリーンショット：対象箇所の特定、現在の文言の引用。
- `references/improvement-playbook.md`：項目別の改善策の引き出し。そのまま使わず、対象サイトに合わせる。
- `references/proposal-format.md`：提案書の構成、優先度の付け方、JSON形式。

### 4. 課題をまとめる

レベル0〜1の項目、致命項目、目的への影響が大きいレベル2の項目を課題にする。
同じ原因から来る項目はまとめる（例：A1とA2を「スマホで連絡手段に辿り着きにくい」）。課題が多いときは影響度の高いものから最大7件程度にし、残りは「その他の改善点」として短く列挙する。読み手が全部を一度に判断できる量に絞るため。

### 5. 施策を具体化する

施策ごとに、次がそろっているか確認する。どれかが一般論のままなら、そのサイトの事実に置き換える。

- **対象箇所**：URL と、ページ内の場所（ヘッダー、ファーストビュー、◯◯セクション、フッター、スマホの画面下部など）。
- **現状**：観測事実と、可能なら現在の文言の引用。
- **問題点**：訪問者（想定顧客）にとって何が困るか。
- **改善内容**：何をどう変えるか。配置、文言案、仕様（項目数・サイズ・色の考え方）。
- **改善後のイメージ**：見出し・ボタン・セクション構成の案。そのサイトのサービス名・地域・強みを使い、未確認部分は【要確認】。
- **範囲**：初期商品（推奨案：1ページサイト＋公開）で対応できるか。範囲外は運営へ相談。
- **企業への確認事項**と**確認方法**（改善後に何を見れば達成か）。

良い点として評価された部分は残す前提で書く。既存の強みを否定しない。

評価の `sales_notes.product_fit` が「範囲外」の場合（例：充実した多ページサイトで、1ページサイトへの置き換えが後退になる）は、作り直しを勧めない。
既存サイトの部分改修として施策を書き、`scope` を要確認にして「初期商品の範囲外。運営判断」と明記する。提供するかは運営が決める（REQUIREMENTS.md §6）。

営業向けの要点では、実際に比較していないのに「地域で一番」「他社より充実」のような比較の言い方をしない。観測した事実だけで話せる言葉にする。

### 6. 書き出す

`references/proposal-format.md` に沿って `$OUT/proposal.md` と `$OUT/proposal.json` を書く。
両方の内容を一致させる（施策ID・優先度・対象箇所）。書き終えたら JSON を `python3 -m json.tool` で検証する。

### 7. 報告

ユーザーに、判定結果、課題の数、優先度「高」の施策、企業への確認事項の数、保存場所を短く伝える。

## 記録

- `generator.model` には確認できたモデルIDを書く。確認できなければ「不明」。
- reports/ は実在企業の情報を含むため Git に入れない。外部への共有・企業への送付はユーザーの指示があるときだけ。
- 再評価・再提案では新しい日付のディレクトリに版を作る。契約で選ばれた提案版は上書きしない（REQUIREMENTS.md §10.3）。
