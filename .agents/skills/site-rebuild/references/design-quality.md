# 改善デモのデザイン品質基準

営業先に見せる画面を「正しいワイヤーフレーム」ではなく「改善後を想像できる完成像」にするための基準。制作前の方針決定と、PC・スマホの実画面レビューで使う。

## 1. design-brief.json

HTMLを書く前に `$OUT/site/design-brief.json` を作る。

```json
{
  "audience": "誰が、どんな状況で見るか",
  "primary_action": "ページを見た人に取ってほしい主な行動",
  "brand_traits": ["信頼感", "親しみ", "地域密着"],
  "preserve": ["元サイトの青", "社名表記", "業務名"],
  "change": ["小さい文字", "同じ強さの情報", "問い合わせの見つけにくさ"],
  "visual_direction": {
    "style": "professional | warm | editorial | bold",
    "hero_layout": "split | centered | statement",
    "section_rhythm": "alternating | continuous",
    "signature_motif": "この会社らしさを出す視覚モチーフを1つ",
    "image_strategy": "approved | generated | abstract | none"
  },
  "content_strategy": "訪問者の疑問をどの順で解消するか",
  "avoid": ["何でもカード化", "根拠のない実績表示"]
}
```

- brand_traits は2〜4個。互いに矛盾する語を並べない。
- signature_motif は、配色だけではない固有の表現にする。例：精密加工なら寸法線、運送なら進行方向を感じる斜線、和食なら余白と縦組み風の見出し。
- 元サイトをそのまま再現する指示ではない。識別に必要な要素を残し、低品質の原因は変える。

## 2. 表示内容と確認事項の分離

営業用デモのHTMLに `【要確認】`、`要確認：`、`TBD`、ダミー値を表示しない。

- 確認済み部分だけで自然な文になるなら、未確認部分だけ省く。
- 項目全体が未確認なら、その行・カード・セクションを省く。
- デザイン上どうしても必要な将来枠は、具体的な事実を装わない説明にする。例：「施工事例は素材確認後に掲載」ではなく、デモでは事例セクション自体を出さない。
- 確認事項は `rebuild.json.needs_confirmation` に残し、運営レビューで扱う。

非公式デモの表示は必要だが、本文より目立つ警告色の大きな帯にはしない。上部の細い帯とフッターに簡潔に表示する。

## 3. 画像

ロゴ、人物、施工実績、店舗外観など企業固有の事実を示す画像は、利用許諾が確認できたものだけ使う。許諾不明の元画像を複製・ホットリンクしない。

画像ごとの利用段階と記録項目は `image-policy.md` に従う。未確認素材は評価参照だけ、営業デモ許可済み素材はローカル保存した期限・閲覧制限付きデモだけ、本番許可済み素材は原則として顧客提供の元データを使う。元サイトのスクリーンショットは改善前の内部証拠であり、改善後デモの素材にしない。

ただし、すべてを灰色のプレースホルダーにする必要はない。

- `approved`：許諾済み素材をローカルに保存して使う。
- `generated`：特定の人物・施設・実績を装わない、業種に合った雰囲気画像を生成する。画像生成手段が利用可能で、画面品質を実質的に上げる場合だけ使う。
- `abstract`：CSS、インラインSVG、幾何学模様、図解など、事実を主張しない視覚表現を作る。
- `none`：タイポグラフィを主役にする。画像枠や「画像予定地」は置かない。

プレースホルダーは運営レビュー画面では使ってよいが、営業用デモのファーストビューでは使わない。

## 4. スマホはPCの縮小版にしない

390px幅では、PCのグリッドを1列に並べ替えただけで完成としない。情報を削らず、最初に「会社・提供内容・次の行動」が分かり、その後も目的の情報を探せる順序へ組み直す。

- ファーストビューでは装飾より会社・提供内容・主要行動を優先する。装飾画像や抽象表現が画面の大半を先に占める場合は、後置・縮小・省略のいずれかを選ぶ。
- 固定下部CTAを出す場合、同じ電話・問い合わせCTAを同時に重ねて表示しない。通常CTA、本文、メニュー、フォーカス、ページ末尾を一部でも覆った状態は不合格とする。
- 長文、大量の実績一覧、多数のカードは、単純に縦へ積まない。主要見出しへの目次、意味単位の区切り、DOM内に内容を保持する `details` 等を使い、目的の情報へ移動できるスキャン経路を作る。
- 本文は原則16px以上、補助文でも14px未満にしない。行間、1行の長さ、段落間隔を実画面で確認し、見出しが1文字ずつ落ちる改行や、窮屈な2列カードを残さない。
- 表は関係が単純なら定義リスト等へ組み替える。行列の比較が必要なら表を保持し、横スクロールの説明、読めるセル幅、見出しとの対応を確保する。「横にはみ出していない」が「読める」の代わりにはならない。
- 390pxに加え、長い語、表、多列情報、固定要素があるページは320px前後でも確認する。通常本文に二方向スクロールを要求しない。
- スマホ品質に未解決の問題があるのに、他項目の点数で埋め合わせない。`scores.mobile` は12/15以上を合格条件とする。

### 実画面の証拠

全長スクリーンショットだけでは、実際の1画面内の階層・文字サイズ・固定要素の重なりを判定できない。全HTMLについて、少なくとも次を保存する。

1. 390×844の `fullPage: false` の先頭画面
2. 同じページの全長画像（全体の密度と反復確認用）
3. 折りたたみメニューがあれば開いた状態
4. 表、長文、大量一覧、固定CTAがあれば、その問題が起きやすい途中位置

PNGは deviceScaleFactor: 1 で撮影し、先頭画面の実ピクセル寸法を390×844、全長を幅390・高さ844以上にする。画像を別状態の証拠として使い回さず、成果物ディレクトリ内の `review/`（`site/` の隣）へ保存する。画像の存在だけでなくPNGの形式・寸法も検査する。

HTML/CSS/JS/画像等を修正したら、点数や画像を流用せず変更後を再確認・撮影する。次のコマンドで現行の表示入力の指紋を取得し、`quality-review.json.site_digest` に保存する。これは撮影自体の証明ではないため、取得した値だけを更新して古い証跡を使わない。

```bash
python3 <skill>/scripts/check_mobile_quality.py --digest $OUT/site
```

`quality-review.json.page_reviews` に各HTMLの証拠とチェック結果を記録する。トップだけ、またはページ種別の代表1件だけでは合格にしない。

```json
{
  "site_digest": "sha256:上記コマンドが返す値",
  "page_reviews": [
    {
      "file": "index.html",
      "mobile": {
        "viewport": {"width": 390, "height": 844},
        "evidence": [
          {"state": "initial_viewport", "screenshot": "../review/index-mobile-viewport.png"},
          {"state": "full_page", "screenshot": "../review/index-mobile-full.png"},
          {"state": "menu_open", "screenshot": "../review/index-mobile-menu.png"}
        ],
        "checks": {
          "horizontal_overflow": false,
          "content_overlap": false,
          "fixed_ui_obscures": false,
          "duplicate_primary_actions": false,
          "text_readable": true,
          "navigation_usable": true,
          "scan_path_clear": true,
          "tap_targets_usable": true,
          "table_content_usable": true
        },
        "observations": ["先頭画面で会社・業務・主要行動を確認"]
      }
    }
  ]
}
```

品質レビューを書いたら、通常の `check.py` に加えて次を実行する。

```bash
python3 <skill>/scripts/check_mobile_quality.py $OUT/site
```

通常の `check.py` は `status: pass` のときこの検査を内部で実行する。単体実行もでき、スマホ単独点、390×844の数値、全HTMLのページ別レビュー、先頭画面と全長PNGの実寸、表示入力の指紋、重なり・可読性等の必須判定を確認する。画像だけから実際の重なりや読みやすさを自動判定するものではなく、各チェックは実画面で確認する。終了コード1なら `pass` にしない。

## 5. 100点の品質レビュー

`$OUT/site/quality-review.json` に採点と根拠を保存する。各項目は、PC 1440px前後とスマホ 390px前後の実画面を見て採点する。

| 項目 | 配点 | 見ること |
| --- | ---: | --- |
| 企業らしさ・業種適合 | 20 | 他社名に替えても成立する凡庸な見た目ではないか。design brief と一致するか |
| 第一印象・視覚階層 | 20 | 最初の数秒で会社・サービス・次の行動が分かるか。見出しと本文の強弱があるか |
| 導線・情報設計 | 20 | 訪問者の疑問順になっているか。CTAが多すぎず、必要な場所にあるか |
| 内容の信頼性 | 15 | 元サイトの固有語・意味・語調を保った完成原稿か。内部注記、ダミー、汎用的な穴埋め、誇張、裏付けのない数字がないか |
| スマホ品質 | 15 | 横スクロール、窮屈なカード、過大な固定要素、不自然な改行がないか |
| 細部の完成度 | 10 | 余白、整列、角丸、罫線、色、フォーカスが一貫しているか |

80点未満、スマホ品質12/15未満、または次の致命項目が1つでもあれば `needs_revision` とし、最大3回まで直して再撮影する。

- 営業用画面に内部向けの確認注記・ダミー値が見える
- ファーストビューの主役がプレースホルダー
- 主要CTAまたは会社・サービスの説明がファーストビューで判別できない
- PCかスマホに横スクロール、重なり、読めないコントラストがある
- スマホで通常CTAと固定CTAが重複・競合する、固定要素が本文や操作対象を一部でも覆う
- スマホでPCの多列要素を1列に積んだだけで、長文・大量一覧・表へ移動するスキャン経路がない
- スマホで本文・表・ボタンが読めないほど縮小・圧縮されている、または不自然な改行が連続する
- PCとスマホで主要本文・主要リンク・ナビゲーションの語や行き先が欠落または不一致
- 固定ヘッダーまたはスマホ下部CTAが、ページ内リンクの到着見出し・入力・Tabフォーカスを完全に隠す
- トップから作成したページへ通常のリンクで到達できない、または詳細ページからトップへ戻れない
- 複数ページで同じtitle・descriptionを使い回す、またはトップの要約を複製しただけのページがある
- 元サイトより情報が欠落し、主要サービスや問い合わせ手段が分からなくなった
- スクリーンショットや評価根拠にある主要ページが未取得なのに、取得済みの薄い材料だけで完成扱いにした
- サービス詳細、実績、年度別表、会社情報等の確認済み情報を、シングルページへ収める目的で省略した
- 年度別・区分別の表をカード化し、見出しと数値の関係または年度の比較を失わせた
- 生成画像を特定の施工・商品・人物・施設の実績写真に見せた
- 静的デモまたは未接続の管理定義を「顧客が編集できる」「受付フォームが動く」と表示・報告した
- 元サイトに名称しかない項目へ汎用説明を足した、または主要本文が元サイトの意味に追跡できない

```json
{
  "status": "pass",
  "attempt": 2,
  "viewports": [
    {"width": 1440, "height": 1000, "screenshot": "../site-review-desktop.png"},
    {"width": 390, "height": 844, "screenshot": "../site-review-mobile.png"}
  ],
  "scores": {
    "brand_specificity": 17,
    "visual_hierarchy": 17,
    "information_design": 18,
    "content_trust": 15,
    "mobile": 13,
    "polish": 8
  },
  "total": 88,
  "fatal_issues": [],
  "observations": ["ファーストビューで業務と連絡先が判別できる"],
  "revisions": ["スマホの見出しを短くし、CTAの折返しを解消"]
}
```

ブラウザを利用できず実画面を確認できない場合は `status: not_run` とし、コード検査の成功をデザイン品質の合格として報告しない。

## 6. 避けるパターン

- すべての情報を同じカードに入れる
- 連続する全セクションで同じ3列グリッドを使う
- ボタン、見出し、枠線のすべてに同じ強調色を使う
- CTAを段落ごとに反復して、どれが主行動か分からなくする
- 業種と無関係なグラデーション、ガラス表現、過剰な影を足す
- 元サイトの低品質な装飾を「同じ会社に見せる」ためだけに再現する
- 情報不足を大量の注意書きや空の画像枠で埋める
- 「1ページだから分かりやすい」を理由に、詳細、実績、会社情報、表を削る
- ページ数を増やすためだけに、同じ要約を複数ページへ分割する
- 全長画像を縮小して眺めただけで、390×844の実画面を確認済みとする
- PCのカード・表・CTAを順番どおり1列化しただけで、スマホ用の優先順位を設計しない
