# SiteOffer

企業サイトの改善機会を自動で見つけ、AIで改善案とサイトを作成し、営業パートナーが提案・契約を進めるサービス。
契約後は運営が制作、クラウド環境の整備、公開まで担当する。

ローカルMVPを開発中です。営業・運営・顧客確認の画面、認証と業務処理、ワーカーとプレビュー配信、改善後サイトのスキル、画像素材の権利管理を実装しています。
ローカルのデモでは、収集から納品・顧客確認まで最後までブラウザで操作できます（生成はモック）。独立した架空企業のDB・メモリキューでは、通常と同じワーカーの構成から、実画像の承認・提案PDF、ChatGPTログインによる提案文・電話台本・FAQ・サイト構成の実生成、写真入りHTMLのDockerビルドまで確認しました。
独立した実PostgreSQL・pg-bossと2プロセスのワーカーでは、架空企業の収集・診断・画像承認・モック提案制作・Astro HTMLまで確認しました。稼働中の通常環境を実生成へ切り替えた運用、実PostgreSQLでの実API・SDKを含む一貫運用、アプリからの画像API実行、企業収集の実API実行、生成サイトのブラウザーによるデザイン再現確認、AWS構築、本番公開、実契約は未実施です。従来の報告は [docs/REPORT.md](docs/REPORT.md)、最新の検証範囲は [docs/DECISIONS.md](docs/DECISIONS.md) の作業記録にまとめています。

## ローカルで起動する

**Dockerがない環境でデモを見る場合**は `pnpm demo` を使います（モックの生成器と架空企業のフィクスチャだけで動き、実在企業・実API・AWSは使いません）。
正常停止後は、同じポート設定で `pnpm demo:resume` を実行すると、初期ユーザー・条件を再投入せず既存データで再開できます。
手順・デモ用アカウント・画面の流れは [demo/README.md](demo/README.md) を参照してください。
実在企業の評価結果（reports/sites、Git対象外）は、`pnpm reports:import` でDBに取り込み、`pnpm demo:promote-imported` でデモのDBに限り営業可能まで進められます（提案文・デモサイトはモックのまま。デモで表示するのは85点以下）。接続先の指定などは [docs/DECISIONS.md](docs/DECISIONS.md) の作業AD・AEを参照してください。

Docker Desktop（Compose v2）、Node.js 24以上、pnpm（指定版は12.11.2）が必要です。
リポジトリのルートで実行します。

```sh
pnpm install --frozen-lockfile
pnpm dev
```

初回は `.env` にランダムなDBパスワードを作り、PostgreSQL 17、Next.js、ワーカー、別ポートのプレビューをDockerで起動します。
マイグレーションと開発用の利用条件・ユーザー作成が完了してからWeb画面が起動します。
既存の `.env` は上書きしません。手動で作った場合は `.env.example` を参考に `POSTGRES_PASSWORD` を設定してください。
通常は [ログイン画面](http://localhost:3100/login) を開きます。

```sh
pnpm dev:users        # 自分の端末で開発用メール・パスワードを表示
pnpm dev:check        # 実DBのログイン・画面応答・役割境界を確認
docker compose ps    # 起動状態
docker compose logs --tail 50 web
pnpm dev:stop        # 停止（DBデータを保持）
```

運営は `ops@example.test` でログインして `/ops`、営業は `sales@example.test` で `/sales` を開きます。
営業の自己登録は `/register` です。仮の利用条件は開発用で、本番用の確定文面ではありません。
起動時のDBは空で、実在企業の取り込み・評価・生成は自動実行しません。
ワーカーは架空企業のフィクスチャ、取得済みの診断データ、モック生成器に固定しています。実Codexの認証情報やAPIキーは渡しません。
閾値は未決の `null` のままで、診断後の自動提案生成は保留になります。
Webは `127.0.0.1:3100`、プレビューは `127.0.0.1:3200`、DBは `127.0.0.1:54329` に限定して公開します。
プレビューの `/` は404が正常です。有効な共有リンクからだけ成果物を閲覧できます。
Composeのポートは `.env` の `WEB_PORT`、`PREVIEW_PORT`、`DATABASE_PORT` で変更できます。DBポート変更時は `DATABASE_URL` も合わせて変更します。

DBデータはDockerの `siteoffer_postgres-data` ボリューム、開発用ログイン情報は `.data/dev-users.json` に保存します。
`.env` と `.data/` はGit対象外です。再起動・再実行でユーザーやパスワードは変わりません。
ワーカーの成果物はGit対象外の `reports/` に保存し、プレビュー側には読み取り専用で渡します。
`docker compose down --volumes` はDBを削除するため、通常の停止には使わないでください。
アプリのコンテナはソースをビルド時にコピーするため、変更の反映には再度 `pnpm dev` を実行します。
このイメージは開発用で、企業ごとの生成コードを実行する隔離イメージとは別です。

### ホスト側で画面を開発する

```sh
pnpm dev:setup
docker compose up --detach --wait db
pnpm db:migrate
pnpm dev:seed
pnpm dev:web
```

ComposeのWebが起動中なら先に `docker compose stop web` を実行します。
ホスト側の `pnpm dev:web` はルートの `.env` を読み、`127.0.0.1:3100` で起動します。Dockerなしの場合は `pnpm dev:db` でPGliteを起動し、
`.env` の `DATABASE_URL` を `.env.example` 内のPGlite用URLに変更してから `pnpm dev:seed` と `pnpm dev:web` を実行できます。
PGliteは開発・テスト用で、実PostgreSQLの同時トランザクション検証を代替しません。

```sh
pnpm check           # 型検査・Lint・自動テスト（外部APIはモック）
```

## 現在のCodexアカウントを生成に使う

現在のCodex desktop/CLIのChatGPTログインを共有します。APIキーは不要です。
通常のComposeワーカーはモックです。実Codexへ切り替える場合は次の順で実行します。

```sh
pnpm dev:setup       # .envがない場合だけ、アプリのローカル設定を用意
pnpm codex:setup      # .envへ認証ファイルの参照・実行UIDを設定し、生成用とビルド用のイメージを作る
pnpm codex:sandbox-check # ダミー認証・ネットワークなしでWindowsのパスや隔離・結果の受け渡しを検査
pnpm codex:lifecycle-check # モデル・DBなしで中断・時間切れ・停止確認・実行分離を実Dockerで検査
pnpm codex:crash-check # 検証用ワーカーの強制終了・専用DBの再オープン・生成保留・残留コンテナの回復を検査（モデルなし）
pnpm site:build-check # モデル・DBを使わず、実Dockerでデモ・納品・開始前の中断と制限時間を確認
pnpm codex:check      # 使い捨てコンテナ内のSDKで短い実応答を確認（Codex利用枠を消費）
pnpm codex:worker     # Composeのモックワーカーを停止し、ホスト側の実ワーカーを起動
```

ワーカーの制御プロセスはホスト側で動かし、Codex SDKはジョブごとのDockerコンテナ内で実行します。
これにより、通常のアプリコンテナへDockerソケットやCodex認証を渡す必要がありません。
実Codexの設定ではサイトのビルドもジョブごとのDockerを必須にし、構成の不備は設定エラーとして返します。Dockerなしの架空モックデモでは、従来のローカルビルダーを使います。
生成用イメージはNode.js 24と固定したSDKから単独でビルドできます。アプリ用イメージの事前ビルドは不要です。
WindowsではDocker Desktopを起動してください。空白・日本語を含むドライブの絶対パスに対応し、認証ファイルの参照先は `.env` にスラッシュ区切りで保存します。
既存デモの稼働確認だけなら、`.env` の作成や実ワーカーへの切替は不要です。上記手順は実Codexを使う通常環境の設定です。
認証を設定せず隔離処理だけ確認する場合は、`docker build -f Dockerfile.codex -t siteoffer-codex:local .` と `pnpm codex:sandbox-check` を使えます。
各実行に固有のIDを割り当て、現在のIDと一致した結果だけを受け取ります。古い生成イメージはIDを返さないため、ランナー更新後は生成用イメージも再ビルドしてください。
生成の中断・時間切れではDockerクライアントと専用コンテナの終了を確認してから戻ります。生成ジョブは停止確認を最大30秒待ち、その間は同時実行枠を保持します。停止を確認できなければ「停止確認待ち」にし、同じ生成方式の新規実行と自動再試行を止めます。マウントした作業データは削除しません。通常のワーカーの毎分の回復処理で、同じホスト・終了済みのクライアント・当該実行の識別ラベルを照合し、停止を確認できたものだけ受付の制限を解除します。遅れて届いた結果は採用せず、必要な再生成は元の依頼から行います。元のホストやクライアントの終了を確認できない場合は制限を維持するため、ワーカー・Dockerの稼働と生成履歴を確認してください。
運営の「処理の状況」の先頭では、全案件の停止確認待ちを20件ずつ確認できます。企業で絞り込んでいても、別企業の生成が同じ方式の受付を止めている場合は表示します。「次に確認すること」で停止情報の不足・対応ワーカーの不在・停止確認への未対応・対応ワーカーの稼働を区別し、対象企業の生成履歴へ移動できます。停止確認への対応通知がない旧ワーカーを、対応済みとは表示しません。画面の表示で停止制限を強制解除したり、生成を開始したりすることはありません。
ビルド用イメージだけを準備する場合は `docker build -f Dockerfile.site -t siteoffer-site:local .` を実行します。ビルドはネットワークなし・非root・読み取り専用のルートで行い、検証した構成と選択画像だけを専用ディレクトリへ渡します。Codex認証・DB接続・APIキーは渡しません。Dockerの各オプションは [公式の実行ガイド](https://docs.docker.com/engine/containers/run/)を参照してください。
ビルドの既定上限は180秒、1 CPU・2GB・256 PIDです。`SITEOFFER_SITE_BUILD_IMAGE`、`SITEOFFER_SITE_BUILD_TIMEOUT_MS`、非rootの数値UID:GIDを指定する `SITEOFFER_SITE_BUILD_USER` で設定できます。セットアップはホストの実行ユーザーに合わせます。入力は1MB、画像32点・1点12MB・合計64MBまで、出力は500項目・128MB・階層16まで検査します。スマホの見た目は、この構造検査とは別に確認します。
ビルドごとに別の出力先を作り、過去の成果物を上書きしません。中断・時間切れでは自身のコンテナだけを停止し、停止を確認できない場合は作業データを残して運営の確認へ戻します。
ホスト側ワーカーはターミナルのCtrl+Cで停止します。モックに戻す場合は、ホスト側を停止してから `pnpm dev` を実行します。
両方のワーカーを同時に動かさないでください。
ワーカーの予期しない終了に備え、Docker開始前・クライアント起動直後・終了時に実行情報を生成履歴へ保存します。実行中の実生成との接続が切れた場合、停止が不明なまま失敗で閉じず、停止確認待ちとして保留します。定期回復前でも、期限切れの実生成が残っていれば新しい実生成を開始しません。元のクライアント・コンテナの停止を確認した後も、遅れた出力や同じジョブを自動採用・再実行しません。開始直前に終了してPID等の情報が残らなかった場合は、安全を確認できるまで保留を維持します。

元の `auth.json` は読み取り専用でマウントし、現在のアクセス認証をコンテナの一時ホームに置きます。
元ファイルの更新トークンをコンテナの認証には使わず、デスクトップとの更新競合を避けます。
期限切れの場合はデスクトップ/CLI側で認証を更新してから再試行します。元の認証ファイルをGitや画面へ出しません。
ホストの `.env` は認証ファイルのパスだけを保存し、トークンは保存しません。

生成モデルの選定は引き続き未決です。`SITEOFFER_CODEX_MODEL` が空ならCLIの既定を使い、応答のモデルIDが取得できなければ不明として記録します。
国税庁・検索・サイト収集は引き続き架空フィクスチャ設定で、評価閾値も `null` のままです。
ローカルの生成ネットワークはDockerの `bridge` です。送信先をOpenAIだけに限定するプロキシは未実装です。
認証共有の公式説明：[Codex Authentication](https://learn.chatgpt.com/docs/auth)。

## デザイン画像から提案資料・サイト制作へ進む

1. 運営の「デザイン・提案書」で制作条件をまとめ、デザイン画像を生成または取り込みます。画像APIを設定しない場合も、imagegen等で作ったPNG・JPEG・WebPを取り込めます。
2. デザインの会社情報・写真の扱い・PCとスマホの構成を確認し、承認します。デザイン提案PDFは、画像と制作条件・更新機能の確認事項をまとめた資料として出力できます。
3. サイトに載せる写真・ロゴは企業詳細の「画像素材と利用許諾」に登録し、実ファイル・利用許可・配置先を確認します。「営業デモで使用可」の素材は次の提案デモへ、「納品サイトで使用可」の素材は納品制作へ渡します。デザイン画像全体はレイアウト参照として扱います。
4. 承認したデザインから制作を依頼します。提案の版ごとに写真・ロゴのID、ハッシュ、許諾の版を固定し、再試行で別の写真に差し替えません。素材の許諾・配置が変わると、その素材を使う提案の既存共有リンクも配信を止めます。同じ内容の保存では許諾の版と共有を維持します。変更後は新しい提案を制作してください。
5. 提案レビューの「画像案と比較」で、その提案の制作元となった承認画像と制作サイトを並べて確認します。画像は全体・実寸で切り替えられ、PC・スマホの切り替えはサイトに適用されます。「制作元の画像・PDF」から同じデザイン版と診断へ戻れます。元画像との対応を確認できない提案には案内を表示し、最新画像で代用しません。

新しく生成する提案・納品サイトは、正式名称・略称・会社情報の表の値・電話の表示とリンク先・メール・受付時間を確認済み情報と照合します。会社情報の参照キーが正しくても値が異なる構成は成功出力として保存しません。表記上の空白・全半角や電話の区切りは許容し、国番号の推測変更や別の屋号の創作は認めません。自由文すべての正しさを保証する検査ではないため、レビューも必要です。保存済みの提案・納品をこの検査で自動的に書き換えることはありません。

デザイン画面にも画像生成ワーカーの受付状況を表示します。開始待ちのAPI生成は「開始前の生成を取り消し、画像取り込みへ」で、同じ版・制作条件を保ったまま取り込みへ切り替えられます。操作履歴に変更前後を残し、ワーカーが取得済みの場合は切り替えません。生成開始後の中断や、実API側の取り消しを行う機能ではありません。

実Codexで承認画像からサイトを作る際は、画像のハッシュを再確認し、配色候補をローカルで抽出します。書体（見出し・本文）、配色、角丸、余白、PCの分割とスマホの表示順などを個別に生成し、業種の共通スタイルより優先します。指定が欠ける、画像が変わる、配色が候補外になる場合は生成を成功にしません。これは構成とHTMLへの反映の検査で、画像と同じ仕上がりの保証ではありません。PC・スマホの見た目は引き続きレビューしてください。視覚設定のない過去の版は既存のプリセットを使います。

既存の提案に素材を後から自動追加することはありません。通常のデモはモック生成のままです。今回の実画像・SDK・PDF・HTMLの検証は、通常データから分離した架空企業のものです。組み込みimagegenの実行は、アプリの画像API接続の確認とは別です。稼働済みのワーカーとプレビューへコード変更を反映するには、それぞれの起動方式で正常に再起動する必要があります。

企業詳細の「制作に使う会社情報」では、電話・メール・受付時間・サービス・業種・所在地を根拠付きで確認できます。確認者・日時・版を保存し、実生成の提案と納品で共通利用します。営業の企業詳細と担当画面にも同じ電話・メールを表示し、内部の確認根拠は渡しません。電話・メールが確認できない場合はモデルを呼ぶ前に停止し、確認画面を案内します。空欄にして取り下げた値を収集データから復活させず、同じ内容の再保存では版を変えません。制作途中や再試行で確認情報の版が変わった場合は、新しい制作版が必要です。

確認情報の版を記録した生成から作った提案・納品は、情報の変更後に共有リンクを停止します。版の記録がない過去の生成は従来の扱いです。保存テーブルはマイグレーション0042で追加し、デモのDBは通常起動時に適用します。動作確認用のモック生成は架空の固定内容を使うため、この確認情報を使う実生成とは区別してください。

## 既存の記事を引き継ぐ

運営の「お知らせ・ブログ」から企業を選び、記事の一括取り込みを開きます。UTF-8のCSV・JSONのほか、[WordPressの標準エクスポート（WXR）](https://developer.wordpress.org/reference/functions/export_wp/)を直接読めます。WordPressの「ツール → エクスポート → 投稿」で、期間を分けて書き出してください。1回100記事・2MBまでです。

WordPressの公開投稿を選択した「ブログ／お知らせ」の下書きへ取り込み、元URLとUTC掲載日時を保持します。日本語など既存のURL名を使えない場合は`wp-投稿ID`へ変換し、元URLは旧URLの引き継ぎで確認できます。取り込み前に対象・本文・利用権利を確認し、既存の記事は上書きしません。

本文はテキストへ変換し、画像・フォーム・埋め込みに確認用の印を残します。画像・添付を自動取得せず、装飾・ショートコード・コメント・作者・カスタム項目・公開状態は引き継ぎません。非公開・下書き・予約・パスワード付き投稿、固定ページ・カスタム投稿・添付は対象外として件数を案内します。記事の保存・掲載と、旧URL・ドメインの移行はそれぞれ確認して進めてください。

## PostgreSQLで並行実行を確認する

Dockerと事前準備した`postgres:17.10-alpine`を使い、専用コンテナで検証します。通常の`DATABASE_URL`やAIの認証を使わず、終了時に所有する検証用DB・ワーカーを停止します。

```sh
pnpm test:postgres:audits   # 診断受付・取り消し・一覧
pnpm test:postgres:sales    # 担当・契約・報酬・抑止と同時操作
pnpm test:postgres:pipeline # 実pg-boss・2プロセスで画像承認後の制作と重複防止
pnpm test:postgres:recovery # 処理中のDB再起動・ワーカー強制終了からの回復
```

パイプラインの取得・生成は架空フィクスチャとモック、HTMLは実際のAstroビルドです。最新の結果は`.data/local-run/postgres-pipeline/latest-result.json`、実行ごとの成果物は同フォルダー内に保存します。実API、画像の品質、公開・契約の受入を証明するものではありません。ローカルの並行ビルドも、ビルドごとに作業ディレクトリを分けて中間ファイルの競合を防ぎます。

回復検証は専用の永続ボリュームと固定のループバックDBポートを使い、診断中にDBを再起動します。続いて診断を取得したワーカーだけを強制終了し、残ったワーカーが通常の生存確認期限・再試行間隔で引き継ぎ、画像承認後に提案まで完成することを確認します。時刻や期限を書き換えずに待つため、数分かかります。結果は`.data/local-run/postgres-pipeline-recovery/latest-result.json`に保存し、終了時は所有ラベルを照合した検証用コンテナ・ボリュームを除去します。実SDK・画像APIの停止確認、複数ホストやすべての障害を検証するものではありません。

## 最新の方針

- 名前：SiteOffer。リポジトリ名：siteoffer。
- 営業ユーザーは営業のみ。企業の候補をユーザー自身に登録させない。
- 企業の候補は運営側の仕組みで自動収集する。地域・業種などで絞り込む。
- GPTのSDKでサイトを作成する。Codex SDKでサイトと提案文章を生成する。生成モデルIDは未決。
- 当面はローカルで動かす。Webアプリ、TypeScript、Next.js＋ワーカー、PostgreSQL、Astroの静的サイト生成。詳細はREQUIREMENTS.mdの24章。
- 企業候補は国税庁法人番号APIと検索系APIで収集する。検索系APIの製品は未決。
- クラウド管理にはAWSを使う。現時点で構築・デプロイは進めない。
- ドメインについて営業ユーザーが希望の聞き取り・提案を行う。実際の設定・移管は運営が担当する。
- 報酬は契約完了で発生する。支払日・金額・キャンセル時の扱いは未決。
- 改善提案書を作る評価の閾値は未決（`config/site-evaluation.json` は `null`）。実在サイトの評価データを見てユーザーが決める。デモの85点以下は仮の表示条件。
- ブログ・お知らせなど顧客が更新できる機能は、全社共通のオプションとして自社アプリの共通更新画面で作る。生成サイトの更新・公開・運用では、AWSと認証以外の外部サービスに依存しない。
- 画像は1点ごとに出所・権利状態・利用範囲を管理し、許諾を確認していない画像はデモ・本番に使わない。

過去のSitePitch、Supabase中心の構成、企業の手動登録を主経路にする案は、最新方針に置き換わっている。
担当の初期値（同時3社・未着手72時間で解除）、共有リンクの有効期間14日、生成の上限（試行3回・15分・同時2）は、アシスタントの推奨をユーザーが承認した値。1ページの商品は推奨のままで、ユーザーの確定指示ではない。
