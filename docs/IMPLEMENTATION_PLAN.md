## 2. ディレクトリ構成と所有

    apps/
      web/              Next.js（App Router）。画面・API・サーバーアクション
      worker/           pg-boss のジョブ実行。収集・診断・生成・期限解除
      preview/          生成サイトと提案リンクの配信。webとは別ポート（11章）
    packages/
      db/               Drizzleスキーマ・マイグレーション・接続・テスト用PGlite
      schemas/          Zodスキーマ（API入出力・診断・提案・生成物）
      core/             業務ロジック（権限・担当・営業活動・契約・報酬・監査ログ）
      discovery/        収集プロバイダ（fixture・国税庁・検索）と重複排除
      audit/            評価スキル（Python）の呼び出しと結果の保存
      generation/       Codex SDKの呼び出し・モック・実行記録・コンテナ実行
    templates/
      astro-site/       生成サイトの共通Astroテンプレート
    docker/             compose・Dockerfile・生成用コンテナ（用意のみ）
    fixtures/           架空企業・取得済みサイト・Codexの固定応答

### 共有ファイルの扱い（衝突を避けるための約束）

- **ルートの設定**（package.json、pnpm-workspace.yaml、tsconfig、Vitest設定、pnpm-lock.yaml）と **マイグレーション** は統合担当だけが変更する。
- DBスキーマはドメインごとのファイル（`packages/db/src/schema/<domain>.ts`）に分ける。タスクは自分の担当ファイルの列を追加できる。テストを通すためにworktreeの中で `pnpm db:generate` を実行してよいが、生成されたマイグレーションは取り込み時に捨て、統合担当がまとめて作り直す。
- 依存パッケージは自分の担当パッケージの package.json にだけ追加してよい。lockfile の衝突は統合担当が `pnpm install` で解消する。
- Zodスキーマはタスクごとのディレクトリ（`packages/schemas/src/<domain>/`）に置き、`packages/schemas/src/index.ts` への追記は統合担当が行う。
- `packages/core/src/index.ts` への export の追記も統合担当が行う。各タスクは自分のディレクトリに `index.ts` を置く。
- 他タスクの担当ファイルを直す必要があるときは、直さずに報告へ書く。
- docs/DECISIONS.md・REQUIREMENTS.md は subagent が編集しない。統合担当が記録する（AGENTS.md の記録義務は統合担当が果たす）。

### 波0で用意したもの（各タスクが使う共通部品）

| 部品 | 場所 | 使い方 |
| --- | --- | --- |
| DBスキーマ | `packages/db/src/schema/*.ts` | `import { companies, assignments } from "@siteoffer/db"` |
| DBの型 | `Db`・`Tx`・`DbOrTx` | 関数は `db: DbOrTx` を受け取り、トランザクションの内外どちらでも呼べるようにする |
| テスト用DB | `import { createTestDb } from "@siteoffer/db/testing"` | テストごとに作って `close()` する |
| 操作主体 | `Actor`（sales / ops / system / customer） | 権限判定と操作履歴に使う |
| 時刻 | `Clock`・`fixedClock()` | `new Date()` を直接呼ばない。テストで時刻を進める |
| 戻り値 | `Result`・`ok()`・`err()` | 想定内の失敗は例外にせず返す |
| 操作履歴 | `recordEvent(db, clock, {...})` | 状態を変える処理は同じトランザクションで必ず呼ぶ |
| 運営設定 | `getSetting(db, key)` | 既定値は `DEFAULT_SETTINGS`（推奨案の3社・72時間など） |
| ポート | web 3100、preview 3200、開発DB 54329 | 3000番はこのマシンの別のプロセスが使っている |

注意：この環境のシェルはメモリ上限4GBの枠（cgroup）で動き、subagentもこの枠を共有するとみられる。PGliteを使うテストは並列数2（vitest.config.ts）で動かし、同時に動かすsubagentは2〜3本にする。

注意：PGliteは単一プロセスなので、テストで `Promise.all` を使っても並行トランザクションは直列に実行される。
同時確保・二重報酬の防止は「一意制約で守られていること」をテストで確かめ、本当の同時実行は実PostgreSQL（Docker環境）で確認する。

## 4. タスクカード

各カードは subagent にそのまま渡せる粒度にしてある。「担当」に書いたパス以外は変更しない。

### T0 基盤・スキーマ・共通契約（統合担当が直列で行う）

- 担当：ルート設定一式、`packages/db`、`packages/schemas` の土台、各パッケージの空の雛形、`fixtures/` の土台、`.gitignore`、`scripts/check.sh`
- 内容：
  1. pnpm workspaces・TypeScript（strict）・Vitest・Lint/Format（Biome推奨）を設定する。Node 24 前提。
  2. Drizzleスキーマを17章の全概念で作る：User、Company、Website、DiscoveryJob/Source、Audit/Finding、Proposal/ProposalVersion、Assignment、SalesActivity、DomainPreference、Product/Terms、Contract、Payment、Reward/RewardAdjustment、GenerationJob、Delivery/Approval、Deployment、ShareLink、AuditEvent。
     状態欄は混ぜない（17章末）。営業拒否は企業共通の抑止状態として Company 側に持つ。
  3. 一意制約を先に入れる：有効な担当は企業ごとに1件（部分ユニーク）、報酬は契約ごとに1件、正規化URLの一意、生成ジョブの冪等キー。
  4. テスト用ヘルパー：PGliteで空DBを作り、マイグレーションを流して返す `createTestDb()`。
  5. 共通の型：`Actor`（userId・role）、`Clock`（テストで時刻を固定）、`Result` 型、監査ログを書く `recordEvent()`。
  6. `scripts/check.sh`：型検査・Lint・全テスト。subagent と統合担当が同じコマンドで検証する。
  7. PGliteのソケットサーバーで web・worker をローカル起動できるか試し、結果を記録する。
- 完了条件：`scripts/check.sh` が成功。スキーマの一意制約をテストで確認。空の各パッケージがビルドできる。

### T1 認証・権限

- 担当：`packages/core/src/auth/`、`packages/core/src/permissions/`、`packages/db/src/schema/users.ts`、`apps/web/app/(auth)/`、`apps/web/lib/session.ts`、`apps/web/lib/auth/`
- 内容：メール＋パスワードの簡易ログイン（パスワードはハッシュ化）、セッション、営業・運営の役割。
  営業ユーザーは自己登録できる。登録時に利用条件（文面は仮置きで版を持つ）への同意を記録し、運営が利用停止にできる。運営アカウントは自己登録させず seed で作る。
  認証は `AuthProvider` インターフェースの裏に置き、将来Cognito等へ差し替えられるようにする（24.2）。
  権限判定は `can(actor, action, resource)` のようなサーバー側関数に集め、画面とAPIの両方から使う。
  営業は他人の非公開案件・契約・報酬・活動メモを読めない。企業共通の状態（担当中・営業拒否）だけは読める（5.1）。
- テスト：役割ごとの許可・拒否の表を作り、AC-17を網羅する。未ログイン・他人の資源・運営設定へのアクセスが拒否されること。
- テスト：利用条件に同意しないと登録できない、利用停止のユーザーがログイン・操作できない。
- 開発用の初期ユーザー作成コマンド（seed）を用意する。パスワードはリポジトリに書かず、実行時に生成して表示する。

### T2 担当確保・営業活動・営業拒否

- 担当：`packages/core/src/assignment/`、`packages/core/src/sales-activity/`、`packages/db/src/schema/assignment.ts`
- 内容：
  - 確保は1トランザクションで判定する。同時に複数人が確保しても有効な担当は1人（一意制約＋競合時は失敗を返す）。
  - 同時担当の上限、未着手の期限解除。値は設定から読み、初期値は推奨案の3社・72時間。
  - 商談中の期限超過は自動解除せず「運営確認待ち」にする。
  - 活動の種類は12.3章の9種。次回対応日、運営への相談。
  - 営業拒否は企業共通の抑止にし、担当解除や再収集で消えない。「今は不要」と「今後連絡しないで」を区別する。
  - すべての変更で AuditEvent を残す。
- テスト：同時確保（Promise.allで並行実行）で有効な担当が1件、上限超過の拒否、期限解除（Clockで時刻を進める）、商談中が解除されない、営業拒否後に誰も確保できない（AC-10〜12）。

### T3 契約・入金・報酬・ドメイン希望

- 担当：`packages/core/src/contract/`、`packages/core/src/reward/`、`packages/core/src/domain-preference/`、対応するスキーマファイル
- 内容：
  - 成約報告（営業）と契約確認（運営）を分ける。確認時に、価格・範囲・提案版・ドメイン対応・継続費用・担当・報酬条件のスナップショットを保存する。
  - 契約完了で報酬を発生させる。確認の再実行で二重に発生しない。
  - 契約・入金・報酬・支払いの状態を別々に持つ。報酬の調整は別の記録として残し、元を消さない。
  - 販売条件・報酬条件が設定されていない案件は営業可能にできない（14章）。
  - ドメイン希望は13章の項目。移管コード・パスワード・鍵の入力欄は作らない。入力に秘密らしき値があれば保存を拒否する。
- テスト：報酬が1回だけ発生する（並行確認を含む）、条件を後から変えても既存契約のスナップショットが変わらない、入金と支払いが別に記録される（AC-13・15・16）。

### T4 企業候補の収集

- 担当：`packages/discovery/`、`fixtures/discovery/`、`packages/db/src/schema/discovery.ts`
- 内容：
  - `DiscoveryProvider` インターフェース：収集条件（都道府県・市区町村・業種・キーワード・上限）を受け取り、出典と取得日時を付けた候補を返す。
  - `FixtureProvider`：架空企業で動く。名古屋近郊のデータを含め、同じ企業の別ドメイン・同名の別企業・第三者サイトだけが見つかる例を入れる。
  - `NtaCorporateNumberProvider`：国税庁法人番号システムWeb-APIのクライアント。アプリケーションIDは環境変数から読み、なければ明確なエラーにする。テストは記録済みの応答で行う。
  - `SearchProvider`：検索APIの製品が未決なので、インターフェースとモックだけ作る。
  - 公式URLの確度（確認済み・候補・確認待ち）。所在地は出典付きで持ち、キーワードだけで断定しない。
  - 正規化URL・法人番号で重複を除く。再実行で増えない。営業拒否・対象外・既存契約先を営業可能へ戻さない。
  - ジョブの件数・成功・失敗・理由を記録する。
- テスト：同じ収集を2回流しても件数が増えない、営業拒否が維持される、確度の判定（AC-01〜03）。

### T5 生成（Codex SDKラッパー・モック・記録）

- 担当：`packages/generation/`、`fixtures/codex/`、`packages/schemas/src/generation/`、`packages/db/src/schema/generation.ts`
- 内容：
  - `Generator` インターフェース：用途（提案文・電話台本・想定問答・サイトデモ・納品サイト・評価書）、入力、出力スキーマを受け取る。
  - `CodexGenerator`：`@openai/codex-sdk` を使う。1ジョブ1スレッドとし、スレッドIDを記録する。SDKの使い方は実装時に公式文書で確認する（10.4章のリンク）。
  - `MockGenerator`：`fixtures/codex/` の固定応答を返す。テストと、この環境での開発に使う。
  - 実行は `SandboxRunner` インターフェースを通す。`DockerSandboxRunner`（24.4の制限を設定する。ここでは動かせない）と、テスト用の `NoopSandboxRunner` を用意する。**コンテナなしで実際のCodexを動かす経路は作らない。**

      4. 担当外で変更が必要な点（共有ファイル・他タスク・スキル・要件の食い違い）
      5. 未完了・未検証の点

## 6. 統合の手順（統合担当）

注意：Agentツールで作るworktreeは、ローカルのmainではなくpush済みの位置から作られる。未pushのコミットがあるときは、subagentに最初に `git log --oneline -1` で起点を確認させ、古ければ `git merge --ff-only main` で最新に合わせさせる。

1. subagentの報告を読み、担当外の変更がないことを差分で確認する。
2. worktree のブランチを main に取り込む（衝突は統合担当が解消する。他人の変更を強制で上書きしない）。
3. 新しいスキーマ変更があれば `drizzle-kit generate` でマイグレーションを作り、`pnpm install` で lockfile を整える。
4. `scripts/check.sh` と `scripts/git-check.sh` を実行する。
5. docs/DECISIONS.md に、波ごとの記録（使用モデルは実行情報で確認できたものだけ、各タスクの検証結果、モック／実物の区別、未完了）を追記する。
6. 波ごとに1コミットで main へ push する（AGENTS.md の手順。pushできなければ停止して報告）。

## 8. リスク

- PGliteのソケットサーバーで pg-boss や Next.js が安定して動かない可能性がある。動かなければ、自動テストはPGliteのまま、画面の起動確認はDocker環境へ回す。
- Codex SDKの構造化出力・usage・モデルIDの取得方法は、実装時に公式文書で確認するまで分からない。取れない値は「不明」として記録する。
- CodexをChatGPTログインでアプリのワーカーから自動実行する使い方は、ローカルの試験に限る。利用条件に合うかは未確認で、本番に進む前にAPIキー方式で確認する（24.3）。
- 並列作業でスキーマの変更が重なる。ドメインごとのファイル分割と、マイグレーションを統合担当だけが作るという約束で抑える。
