## C003 — アシスタントの回答

日時：2026-10-14T12:37:39+09:00

おすすめは、**「営業するユーザーが、企業の候補・改善根拠・提案デモを受け取り、受注すると報酬を得られるサービス」**としてMVPを作ることです。

構想の中心は、サイトの採点よりも、**仕事を探すところから営業の準備までを短くすること**にあります。ただし、「電話するだけで売れる」は検証が必要な仮説です。企業の予算や更新時期、既存の制作会社との関係も成約に影響します。

日本の中小企業向けに始める前提で、推奨・疑問点・決めることを整理します。

**1．最初に、ユーザーの役割を決める必要があります**

クラウドワークスでは、発注者が仕事を出します。今回の構想では、企業はまだ発注していないため、ユーザーが見つけるものは「営業先候補」です。ここを明確にすると、サービスの設計が決まります。

| 形式 | ユーザーの担当 | 運営の担当 | 向いている場合 |
|---|---|---|---|
| 営業パートナー型 | 電話・商談・受注支援 | 契約・制作・納品・保守 | 営業だけで参加できるサービスにしたい |
| 制作者支援型 | 営業から制作・納品まで | 調査・診断・提案作成ツール | フリーランスの制作者を支援したい |
| 分業マーケット型 | 営業担当と制作担当が別々に参加 | マッチング・決済・品質管理 | 将来的に大きな市場を作りたい |

**今回の説明に最も近いのは営業パートナー型です。**
その場合、受注後に制作を引き受ける体制が必要です。最初は運営または少数の提携制作者で対応し、営業と制作の両方を自由参加にする仕組みは後から追加するのを勧めます。

**2．MVPは「1業種・1商品・少人数」で始めるのがおすすめです**

最初の対象は、例えば「特定地域のリフォーム会社」のように絞ります。業種をそろえると、診断基準・デザイン・営業説明を再利用できます。実際の対象は、あなたが企業や営業担当者に接点を持っている業種を優先すると検証しやすいです。

基本の流れは次の形です。

**営業先を探す → サイトを診断 → 営業先を確保 → 改善デモを生成 → 電話・商談 → 契約 → 制作・納品 → 報酬支払い**

MVPに入れる機能は、以下に絞ります。

| 機能 | MVPでの内容 |
|---|---|
| 営業先の登録 | ユーザーによるURL入力＋運営が用意した候補 |
| サイト診断 | スマホ表示、表示速度、サービス説明、問い合わせ導線など |
| 提案資料 | 根拠のある改善点3件と、営業で使える説明 |
| 改善デモ | トップページ1枚。スマホ・PC表示に対応 |
| 営業管理 | 未着手・架電済み・商談・失注・受注 |
| 重複防止 | 同じ企業への営業状況を共有し、期限付きで担当を確保 |
| 運営管理 | デモの確認、契約状況、納品状況、報酬管理 |

最初は、全国規模の企業自動収集、全ページの自動制作、複雑な決済・報酬分配まで作る必要はありません。**安価な一次診断を先に行い、ユーザーが営業を進める企業だけデモを生成する**と、生成費用と確認作業を抑えられます。

また、売る商品も固定した方がよいです。ページ数、修正回数、問い合わせフォーム、納期、保守範囲を決めておかないと、営業担当が約束した内容と制作側の対応範囲がずれます。

**3．評価は「サイトの問題」と「買う可能性」を分けるべきです**

ここが事業上の大きな疑問点です。**改善点の多いサイトでも、企業が改善にお金を払うとは限りません。**

アプリには、次の二つを別々に表示することを勧めます。

- **改善の必要性：** スマホで操作しづらい、サービス内容が分かりにくい、問い合わせ先が見つけにくい、といった確認できる問題。
- **営業の優先度：** サイトが集客に関わる業種か、具体的な改善提案を作れるか、公開情報から更新需要の手掛かりがあるか。予算や意思決定者は商談で確認。

「52点なので改修が必要」と言うより、**「スマホで問い合わせボタンを見つけにくいため、常時表示する案を用意しました」**と説明できる方が、提案の根拠が伝わります。

診断結果には、対象URL、確認日時、画面や測定値、改善案を付け、AIの推測は区別してください。GoogleのPageSpeed Insightsも、模擬環境の測定と実際の利用者データを分けており、測定点数だけでは実際の利用体験を断定できません。[Google公式説明](https://developers.google.com/speed/docs/insights/v5/about)

**売上増加・問い合わせ増加・検索順位向上は、診断段階では保証しない設計**にします。アクセス解析がなければ、現在の成果や改善効果は分かりません。

なお、企業サイトの技術情報を使った営業先抽出にはBuiltWith、AIによるサイト構成・ワイヤーフレーム作成にはRelumeがあります。これらを踏まえると、差別化の候補は、**「診断から営業、受注後の納品までつながること」**です。これは現時点では事業仮説です。[BuiltWith](https://builtwith.com/lead-generation)、[Relume](https://www.relume.ai/resources/docs/building-a-sitemap-with-ai)

**4．構想で特に確認したい疑問点です**

- **企業は何にお金を払うのか。** 見た目の刷新、問い合わせ獲得、採用、更新作業の簡略化では、提案も商品も変わります。
- **電話するユーザーは誰か。** 営業経験者、副業初心者、Web制作者で、必要な支援が違います。初心者向けなら、台本に加えて商談同席や引き継ぎ先が必要になる可能性があります。
- **どこまで行えば報酬が発生するのか。** アポイント取得、契約締結、顧客の入金確認のどれかを決める必要があります。
- **成約後に利益が残るか。** 制作費だけでなく、営業報酬、デモ生成、修正、顧客対応、保守を含めて判断します。
- **同じ企業への営業集中をどう防ぐか。** 担当確保の期限、放置時の解除、営業拒否の共有が必要です。
- **既存サイトの何を引き継ぐか。** ドメイン、メール、予約機能、既存URL、更新機能などによって、納品の難しさが変わります。

特に採算は、次の式で案件ごとに確認します。

**販売額 − 営業報酬 − 制作費 − 調査・生成費 − 修正・対応費 − その他の費用**

受注件数だけを追うと、売れているのに利益が残らない状態になり得ます。

運営面では、提案デモに「非公式の改善提案」と明記し、閲覧制限を付けることを勧めます。元サイトの写真・文章・ロゴを使う権利は、企業側も含めて確認が必要です。閲覧制限だけで利用許諾の問題が解消されるわけではありません。[文化庁の説明](https://www.bunka.go.jp/seisaku/chosakuken/taisetsu/index.html)

企業の担当者名や代表者名も個人情報に該当します。MVPでは企業の代表窓口を中心に扱い、個人情報を保存・ユーザーに提供する場合の取り扱いを設計してください。[個人情報保護委員会](https://www.ppc.go.jp/all_faq_index/faq2-q2-6/)

**5．あなたが決めるべき点と、私の推奨初期値です**

| 決めること | 推奨初期値 |
|---|---|
| 参加ユーザー | 営業に関心がある、事前に確認した少人数 |
| ユーザーの担当範囲 | 営業。技術的な商談は運営が支援 |
| 対象企業 | 接点のある地域・業種に限定 |
| 販売商品 | 範囲と価格を固定した小規模サイト改修 |
| 顧客との契約主体 | 運営が契約し、制作・納品を管理 |
| ユーザーへの報酬 | 顧客の入金確認後に支払う成果報酬 |
| サービスの収益 | 制作案件の粗利。利用料課金は実績を見て判断 |
| デモの生成時期 | ユーザーが営業先を選んだ後 |
| 品質確認 | 企業へ提示する前に人が確認 |
| 最初の検証 | 候補20〜30社、営業ユーザー3〜5人程度の小規模実験 |

検証では、電話件数だけでなく、**提案閲覧率、商談率、受注率、受注までの作業時間、案件利益、ユーザーが継続して営業するか**を記録します。この件数は検証規模の仮案で、成約率の予測ではありません。

最初に回答いただきたいのは、次の4点です。これが決まれば、MVPの画面・機能・運営フローまで具体化できます。

1. **ユーザーには営業だけしてもらいますか。それとも制作・納品まで担当してもらいますか。**
2. **成約後の制作を、あなた側で引き受けられる体制はありますか。**
3. **最初に狙いたい業種・地域、または接点のある企業はありますか。**
4. **顧客に売りたいものは、サイト全面リニューアル・一部改善・月額保守のどれに近いですか。**

## C005 — アシスタントの回答

日時：2026-10-14T12:57:19+09:00

この構想なら、**SitePitch（サイトピッチ）**をおすすめします。Webサイトの改善案を作り、企業へ提案するサービスだと伝わりやすい名前です。

| サービス名 | リポジトリ名 | 名前の意図 |
|---|---|---|
| **SitePitch** | `sitepitch` | サイト改善を提案・営業する。今回の構想に最も合う |
| WebRelay | `webrelay` | 運営が用意した提案を営業ユーザーにつなぐ |
| SiteScout | `sitescout` | 改善機会のある企業サイトを見つける |
| SiteOffer | `siteoffer` | 企業に具体的なサイト改善案を届ける |
| WebBridge | `webbridge` | 企業・営業担当・AIによる制作をつなぐ |

**単一リポジトリなら `sitepitch`、アプリだけを分けるなら `sitepitch-app`** が扱いやすいです。商標・ドメイン・既存サービス名の重複は未確認です。

いただいたコメントは、次の前提として整理しました。

- 営業パートナー型で、ユーザーは営業のみを担当。営業できる人が参加できるサービスにします。:codex-annotation{index="1"} :codex-annotation{index="6"} :codex-annotation{index="11"}
- 営業候補は運営が用意し、名古屋近郊などの地域で絞り込める形にします。:codex-annotation{index="2"} :codex-annotation{index="13"}
- 報酬の発生条件は契約完了。同じ企業への重複営業は、担当確保・期限・営業状況をアプリで自動管理する方針です。:codex-annotation{index="7"} :codex-annotation{index="9"}
- 評価基準、商品仕様、採算の詳細は後で検討。既存サイトの引き継ぎ範囲も後で決め、初期対応は狭くします。:codex-annotation{index="3"} :codex-annotation{index="4"} :codex-annotation{index="8"} :codex-annotation{index="10"}
- クラウド環境の整備まで完結させる方向と、AIの改善提案のみを提供する方向は、提供範囲の整理が必要です。公開まで含めるなら、初期商品は**小規模サイトのリニューアル＋公開環境の整備をまとめた買い切り型**を推奨します。提案のみを売る場合にも、`SitePitch` は使える名前です。:codex-annotation{index="5"} :codex-annotation{index="12"} :codex-annotation{index="14"}

## C010 — アシスタントの回答

日時：2026-10-14T13:04:45+09:00

**MVPは「運営が用意した企業に、営業ユーザーがAI製の改善サイトを提案し、契約後は運営側で制作・クラウド整備・公開まで完結するアプリ」**として具体化します。仮称は **SitePitch**、リポジトリ名は `sitepitch` とします。

営業パートナー型、運営による候補提供、ユーザーは営業のみ、契約完了時に報酬発生、公開まで対応する方針は確定です。以下の細部は、実装に向けた推奨仕様です。

**1．最初に販売する商品**

初期商品は、**小規模な企業向けの「1ページサイト制作＋公開環境の整備」**を勧めます。

サービス紹介、会社情報、実績、問い合わせ先を1ページにまとめ、スマホ対応・独自ドメイン接続・HTTPS・公開まで行います。問い合わせは、まず電話・メールへのリンクに絞ります。

予約、決済、会員機能、既存メールの移行などは初期対象から外します。既存サイトにそうした機能がある企業は、営業候補の公開前に運営が確認します。

**制作は買い切り、公開後のホスティング・保守は月額**という商品構成を推奨します。初期費用と継続費用は、営業資料と契約画面で一緒に提示します。価格や報酬額は後で決められるよう、管理画面の設定にします。

**2．営業ユーザーが行うこと**

アプリ内の流れを、次の形にそろえます。

**企業を探す → 担当を確保 → 提案を確認 → 電話 → 商談・契約 → 報酬確定**

企業の詳細画面には、以下をまとめます。

| 表示内容 | 用途 |
|---|---|
| 企業名・地域・業種・現在のサイト | 営業先を選ぶ |
| 改善点とその根拠 | 提案する理由を理解する |
| 改善後のサイトデモ | 企業に完成イメージを見せる |
| 商品の範囲・販売価格・営業報酬 | 条件を確認する |
| 電話台本・想定質問への回答 | 営業を進める |
| 活動履歴・次回対応日 | 継続対応を管理する |

営業ユーザーには、制作、サーバー設定、ドメイン操作を担当させません。技術的な質問や個別の要望は、アプリから運営に引き継げるようにします。

**3．企業候補と提案は、運営が準備する**

最初は運営が企業情報を登録・一括取り込みし、地域や業種で分類します。地域は都道府県・市区町村で絞り込めるようにし、名古屋市、春日井市、日進市などから開始できます。

候補の準備は、次の流れです。

**企業登録 → 現在のサイトを確認 → AI診断 → 改善デモ生成 → 運営確認 → 営業候補として公開**

MVPでは少数の候補を扱い、**提案まで準備できた企業を一覧に出す**形を勧めます。ユーザーが選んだ後、すぐ営業を始められるためです。

評価基準の詳細は後で詰めますが、各改善点に「確認した事実・改善案・対象URL・確認日時」を持たせます。AIが作る文章には、未確認の実績、資格、料金などを勝手に追加させません。

提案デモは本番サイトと区別し、企業に共有するリンクには有効期限と閲覧制限を設けます。

**4．営業先の担当管理は、アプリで自動化する**

担当管理はMVPの中心機能です。初期ルールとして、以下を提案します。

| 状況 | アプリの処理 |
|---|---|
| 担当確保 | 同じ企業を同時に担当できるのは1人 |
| 確保数 | 1人につき進行中の企業は最大3社 |
| 未着手 | 確保後72時間、活動記録がなければ自動解除 |
| 営業継続中 | 次回対応日を登録し、期限前に通知 |
| 商談中に期限超過 | 自動で再配布せず、運営確認待ち |
| 営業拒否 | 全ユーザーから営業対象外にする |
| 契約完了 | 営業一覧から外し、納品工程へ移す |

営業結果は「不在」「再連絡予定」「商談中」「失注」「営業拒否」などをユーザーが記録します。**拒否された企業を、別のユーザーに自動で回さない**仕様にします。

担当確保はデータベース側で一括処理し、同時にボタンを押しても二重確保が起きないようにします。

**5．契約・報酬・公開の扱い**

企業との契約主体は運営にそろえます。営業ユーザーによる「成約しました」という報告だけでは確定せず、運営が契約書等を確認して、契約完了にします。

- **報酬の発生：** 契約完了時。
- **報酬額：** 契約時点の条件を保存。後から設定を変えても、その案件には反映しない。
- **支払い管理：** 発生・支払い予定・支払い済みを分ける。
- **入金管理：** 顧客の入金状況を別に記録し、報酬発生と混同しない。

支払日やキャンセル時の扱いは、実際の営業開始前に定めます。

契約後は、運営側で次の工程を進めます。

**掲載内容・素材の確認 → AIで制作 → 運営確認 → 顧客確認 → 公開環境の整備 → 公開**

初期のクラウド整備は、静的サイトのホスティング、ドメイン接続、HTTPS、稼働監視、復元用データの保存に限定します。ドメインの権利は企業に残し、運営が設定を支援する方針を勧めます。

**6．作る画面と技術構成**

営業ユーザー用は、以下の5画面に絞ります。

1. ログイン・利用条件の確認
2. 企業一覧・地域／業種フィルター
3. 企業詳細・改善提案・デモ
4. 担当案件・活動記録・運営への引き継ぎ
5. 契約実績・報酬一覧

運営用には、企業登録、AI処理・提案の確認、営業状況、契約・報酬、制作・公開の管理画面を用意します。

技術構成の第一候補は、**Next.js＋Supabase＋別の実行環境で動くAI処理ワーカー**です。画面とAPI、認証・データ保存、時間のかかる診断・生成を分担できます。営業担当が他人の非公開案件を扱えないよう、サーバー側の権限管理を組み込みます。[Next.js公式](https://nextjs.org/docs/app/getting-started/route-handlers)、[Supabase公式](https://supabase.com/docs/guides/database/postgres/row-level-security)

**7．開発の順番とMVPの完成条件**

まず、準備済みの提案を使って営業管理を作り、その後にAI診断・生成、最後に制作・公開管理をつなぎます。AIの出力品質と、営業アプリとしての使いやすさを、それぞれ確認できる順番です。

MVPの完成条件は、**運営が登録した1社について、ユーザーが担当を確保し、提案・営業・契約確認・報酬発生・サイト公開まで一連の操作で進められること**です。デモ上の契約・公開と、実際の契約・公開は明確に区別します。

実装はこの仕様で進められます。事業側で営業開始までに決める数値は、**販売価格、月額費用、営業報酬額、報酬の支払日**です。評価基準や採算の詳細は、希望どおり後の工程で詰められます。
