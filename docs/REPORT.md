# SiteOffer 作業報告書

作成日：2026-10-14

SiteOfferは、2026-10-14の1日で要件定義からローカルで最後まで操作できるデモまで到達しました。ただし生成はモック、企業収集は架空データと手作業の評価で、実APIによる一連の処理・AWS公開・実契約はいずれも未実施です。

構成は [docs/DECISIONS.md](DECISIONS.md) 7章「最終報告書の構成」に従っています。

## 1. 目的と背景

中小企業のWebサイトをAIで診断し、改善後のサイトを提案して、営業パートナーが売るサービスです。クラウドワークスのように営業が案件を選ぶ「営業パートナー型」を採りました。

- **対象ユーザー**：営業できる人なら誰でも（自己登録＋利用条件への同意）。営業は営業だけを担当する
- **運営**：企業候補の自動収集、診断・提案の確認、制作、ドメインの実作業、AWSでの公開
- **顧客企業**：共有リンクで提案デモを見て、納品物を確認・承認する
- **解決したい課題**：古いサイトを持つ企業を見つけ、根拠のある改善案と完成イメージを営業がすぐ出せるようにする

今回は利益を優先事項にせず、狭く始めてローカルで動くテスト版を作ることを目標にしました。

## 2. 要件決定の過程

判断はNo.1〜75の75件を記録しています（docs/DECISIONS.md 4章）。アシスタントが選択肢と推奨案を出し、ユーザーが選ぶか注釈で答える形で進めました。推奨を採らずユーザーが別の案を決めた主なものは次のとおりです。

| 判断 | ユーザーの決定 | 置き換えた案（推奨・旧案） |
| --- | --- | --- |
| 提供範囲 | AIでのサイト作成からクラウド整備・公開まで | 当初の「改善内容の提案のみ」 |
| クラウド | AWS（実環境の構築は今は行わない） | Supabase中心の構成 |
| 生成のSDK | Codex SDKでサイトと提案文章の両方を作る | 公式openai SDK＋Responses API |
| 企業収集 | 国税庁法人番号API＋検索API（製品は後で比較） | 架空データで仕組みを先に作る |
| 営業の参加 | 自己登録＋利用条件への同意 | 運営による作成・招待 |
| 提案書の閾値 | 実在サイト数十件を評価してからユーザーが決める | 60点未満などの仮値 |
| 営業中の期限切れ | 自動で担当を解除する | 運営確認待ち（現状維持） |
| 顧客が更新できる機能 | 全社共通オプションとして用意。AWSと認証以外は外部に依存しないため、自社の共通更新画面で作る | 更新代行＋外部埋め込み、ヘッドレスCMS（SaaS） |
| 記録 | docs/DECISIONS.md 1つに追記し、会話原文も付録に残す | 会話原文の削除 |

アシスタントやsubagentが仮に決めた細部（報酬の端数処理、担当の初期値、生成の上限など）は、16:57に選択式でまとめて確認し、承認を得ました。権限の既定（ワーカーは全許可、顧客は全拒否から始める）はまだ確認していません。

## 6. 未達と限界

最大の未達は、実際の企業を対象に「自動収集→AI生成→公開」を一度も通していないことです。自動収集、生成、公開、受注、利益はいずれも実現していません。

- **未決**：改善提案書を作る閾値（正の設定は null。デモは仮に85点以下を表示）、致命項目の扱い、生成モデルID、検索APIの製品、本番の認証基盤、AWSの実行方式、価格・報酬額・商品の細目、利用条件の文面
- **未実装**：顧客が更新できる共通更新画面、画像素材ファイルのアップロード・保管とAstroビルドへの受け渡し、生成の送信先制限（プロキシは案のみ）、Astroビルドのコンテナ隔離、運営確認済みの事実を生成に渡す経路
- **未検証**：実PostgreSQLでの同時実行、Docker内でのCodex生成、改善後サイトの実画面品質、スマホ幅の画面、一部画面（並び替え等）のブラウザ表示
- **制約・失敗**：subagentを同時に多く動かしてメモリ上限4GBでテストが落ち、並列数を2に制限した。ワークフローでの7社の生成は権限拒否で全件停止し、再実行した
- **デモの限界**：提案文・デモサイトは全社で同じ架空企業の内容。デモのDBは pnpm demo:reset で消える。改善後サイトには企業の確認待ちの【要確認】が1社18〜26種類残る
- **記録**：作業記録の見出し「AD」「AE」「AO」が重複している。Codexでの一部作業はモデル名が不明
