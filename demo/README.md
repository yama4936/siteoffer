# ローカルの一括起動

ブラウザでSiteOfferの流れを確認するための一括起動です。既定は**モックとローカルだけ**で動きます。実生成には、下記の明示的な切替が必要です。

- 実在企業への連絡・実在サイトへのアクセスはしません。企業候補は架空企業のフィクスチャ（`fixtures/discovery`）、
  診断の収集は取得済みの `fixtures/audit/collected/kakuu-koumuten.collected.json`（架空）を全社で共通に使います。
- 生成はモック（`fixtures/codex` の固定応答）です。生成の入力も `fixtures/codex/input.json`（架空企業「株式会社あおば工務店」）に固定するため、
  **どの企業の提案・デモサイト・納品サイトも同じ架空企業の内容**になります。モックでの成功は実生成の成功ではありません。
- 実Codex・国税庁API・PageSpeed Insights・AWS・Dockerは使いません。ルートの `.env` は読まず、実APIのキーは子プロセスへ渡しません。
- 評価設定は `config/site-evaluation.demo.json`（**デモ用の仮値。ユーザーが決めた値ではない**）を使います。
  正の設定 `config/site-evaluation.json` の閾値は `null`（未決）のままです。
- 販売条件・報酬条件の版 `demo-2026-10`（価格30万円・月額5千円・報酬は価格の10%）も**デモ用の仮値**です。

## 起動・停止

Node.js 24以上と pnpm、`python3`（診断の採点スクリプト）が必要です。リポジトリのルートで実行します。

```sh
pnpm install
pnpm demo          # 起動。データは .data/demo に残る（Git対象外）
pnpm demo:resume   # 既存データで継続起動。初期ユーザー・条件を投入しない
pnpm demo:reset    # .data/demo を消してから起動（作り直し）
pnpm demo:users    # 別の端末で、デモ用アカウントのメール・パスワードを表示
```

`pnpm demo` は次を順に起動し、**Ctrl+C で全部止めます**（どれかが異常終了したときも全部止めます）。
`pnpm demo:resume` は初期データの投入を省き、既存DBと共有復旧鍵がある場合だけ起動します。正常停止後の更新・再開に使用します。既存のアカウント・条件はそのまま利用し、鍵がない場合に新しい鍵を自動で作りません。`--reset`との併用は拒否します。DBのマイグレーションは通常どおり適用します。

| 役割 | 場所 | 内容 |
| --- | --- | --- |
| DB | 127.0.0.1:54329 | PGlite（`.data/demo/pglite`）。起動時にマイグレーション |
| シード | — | デモ用アカウント・利用条件・販売条件／報酬条件の版（何度実行しても増えない） |
| web | http://localhost:3100 | Next.js（開発モード） |
| プレビュー | http://localhost:3200 | 共有リンク（`/s/<token>/`）からだけ成果物を配信。`/` は404が正常 |
| ワーカー | — | pg-boss のキュー＋DBの受付処理（3秒ごと） |

- ポート 54329・3100・3200 のどれかが使用中なら起動しません。`pnpm dev:db`・`pnpm dev`（Docker）・別の `pnpm demo` を止めてから実行します。
- 成果物（デモサイト・納品サイト・診断結果）は `.data/demo/artifacts`・`.data/demo/audits` に置きます。
- DBはPGlite（1セッション）です。受け口（`packages/db/src/pglite-server.ts`。`pnpm dev:db` と共通）が、問い合わせ・トランザクションの単位で接続を順番に処理します。
  実PostgreSQLでの同時実行の検証の代わりにはなりません。

## 実生成を明示して選ぶ

`pnpm demo:codex` は、既存の `.data/demo` を使う実生成の一括起動です。新しいDB・ユーザー・条件は投入しません。通常のデモや復元確認とは区別し、`--reset`、国税庁の実収集、復元確認用プロファイルとの併用を拒否します。**起動後に依頼した診断・提案・納品は、Codexの利用枠を消費します。**

1. ルートの `.env` または起動する端末に、準備済みの `SITEOFFER_CODEX_IMAGE`、`SITEOFFER_CODEX_NETWORK`、`SITEOFFER_CODEX_AUTH_FILE` を設定します。認証は既存のChatGPTログインファイルの絶対パスです。モデルIDは明示した既存設定を使い、未指定ならSDKの既定を維持します。サイトのビルドもDocker必須です。イメージの準備・更新はルートREADMEの手順で行ってください。

   出口プロキシを使う場合は、[専用ネットワークとプロキシ](../docker/README.md#生成用コンテナのネットワーク送信先の制限)を先に用意し、`SITEOFFER_CODEX_HTTPS_PROXY`も設定します。プロキシ利用中の生成はInternal=trueのbridgeでのみ開始します。これは`demo:doctor`でも確認でき、実モデルを呼びません。未設定の場合は送信先を制限しない従来の設定です。用意しただけで現在のデモが実生成へ切り替わることはありません。
2. 通常画面を動かしたまま `pnpm demo:doctor` を実行できます。同じ `DEMO_DB_PORT` を端末へ設定してください。DB・共有復旧鍵、認証ファイルの存在と権限、DockerのLinuxコンテナ、制作イメージと現在のソースの一致、ネットワークの存在、Pythonと、未完了処理・稼働通知を確認します。旧イメージ・ハッシュ未記録のイメージでは実生成の起動を止め、`pnpm codex:build`／`pnpm site:build`での更新を案内します。これらのビルドは認証や`.env`を変更しません。認証内容・秘密値は表示せず、事前確認ではモデル・コンテナ・サーバーの起動、イメージの取得、データ更新はしません。未設定・未確認・未完了があれば終了コード1になります。停止済みDBの件数はこのコマンドでは確認できず、起動時に再確認します。
3. 切替前に、元のモードの「処理の状況」で待機・実行中・停止確認待ちを解消します。通常停止後、同じポート設定のまま `pnpm demo:codex` を実行します。起動条件が不十分ならDB開始前に終了します。条件が揃えば既存DBを開き、受付・引き継ぎ・画像承認後の制作・制作キュー・工程台帳まで再確認してからワーカーを起動します。稼働通知は異常終了から最大45秒残る場合があります。

```sh
pnpm demo:doctor    # 読み取り専用。モデル通信なし
# 元のモードで未完了の処理を確認し、通常停止した後
pnpm demo:codex     # 実生成を選んで既存DBを継続起動
```

実生成は会社ごとの確認済み情報・診断を使い、サイト取得はPython、生成とビルドはDockerで実行します。企業収集・検索はこのモードでは停止し、国税庁の実収集は従来の別起動で行います。画像生成APIは有効にせず、生成済み画像をデザイン画面で取り込んで確認・承認できます。過去のモック診断や固定HTMLが実データへ置き換わることはありません。実サイトの制作前に、出典・会社情報・新しい診断・画像の利用範囲を確認してください。

事前確認では、必須イメージ名の未設定・タグの形式・Dockerからの参照失敗・制作ソースとの不一致を分けて案内します。未設定の場合は使用するタグを指定し、再ビルドが必要かはその後の照合で確認します。「未完了の業務処理」と「方式切替前の稼働確認」も別の項目です。業務0件でも稼働通知が残っていれば終了コード1になります。動作中のデモを準備確認のために止める必要はなく、実際に方式を切り替える直前に通常停止と再確認を行います。

評価設定は明示した `SITEOFFER_EVAL_CONFIG`、未指定なら `config/site-evaluation.json` を使います。未決の閾値をデモ用の仮値で補いません。認証ファイルの存在はログインの有効性、イメージのソース一致は生成品質、ネットワークの存在は送信先制限・接続成功を証明しません。これらの実動作確認は事前確認と別に必要です。

モックへ戻す際も、実生成側で未完了処理を解消して正常停止してから `pnpm demo:resume` を使います。選択した方式は既存の操作履歴に記録し、別方式へ切り替えるときに待機を持ち越しません。同じ方式での継続起動は、従来どおり未完了処理の回復を許可します。共有復旧鍵とアカウントは保持します。

## デモの流れ

2026-10-14 にブラウザ（ヘッドレスChrome）で最後まで通して確認した手順です。ボタン名は画面の表記のとおりです。

**手元のブラウザで見るとき**：VS Code のリモート接続なら「ポート」タブで **3100 と 3200 を同じ番号のまま**転送します。
web はプレビューを `localhost:3200` として埋め込み、プレビューは `localhost:3100` からの埋め込みだけを許可するため、番号が変わると表示されません。

1. **収集**（運営）：`http://localhost:3100/login` で運営アカウントでログインすると `/ops` に移ります。
   「1. 収集・候補」で取得元 `fixture`、都道府県「愛知県」、市区町村「名古屋市」を入れて「ジョブを登録」。
   数秒で架空企業6社が入り、公式サイトが確認済みの3社は診断・生成へ自動で進みます（残り3社は公式サイトの確認待ちで止まるのが正常）。
   再読み込みすると状態が更新されます。
2. **診断・レビュー**（運営）：「2. 診断・生成・レビュー・営業可能化」に「運営確認待ちの提案版」が出ます。
   企業名から詳細（診断の根拠・公式サイト・出典）を確認し、「承認」。
3. **営業可能化**（運営）：同じ画面の「営業可能化を待つ候補」で条件の版 `demo-2026-10` を選び「営業可能にする」。
4. **担当確保・活動記録**（営業）：別のブラウザ（またはシークレットウィンドウ）で営業アカウントでログインすると `/sales/companies` に移ります。
   企業を開いて「この企業の担当を確保する」→ 担当案件の画面で「活動を記録する」（例：提案送付）。
   営業2で同じ企業を確保しようとすると、担当の重複として断られます。
5. **提案の共有**（営業）：担当案件の画面の「提案を共有」で「共有リンクを発行する」。表示されたURL（`http://localhost:3200/s/<token>/`）を
   ログインしていないブラウザで開くと、上部に「非公式の改善提案デモ」と出たデモサイトが表示されます。URLは一度しか表示されません。
6. **ドメイン希望・成約報告**（営業）：「ドメイン希望の聞き取り」で希望を記録 →「成約を報告する」（条件の版と契約資料の参照を入れる）。
7. **契約確認**（運営）：「4. 商品条件・契約・入金・報酬」で「確認を開始」→「契約完了を確認」。
   報酬が1件だけ発生します（デモの条件では販売価格30万円の10%＝3万円）。営業側は「実績・報酬」で確認できます。
8. **納品・顧客確認**（運営 → 顧客）：「5. 制作・ドメイン希望」で「納品を作成する」→「制作に進める」。
   数秒〜数十秒でワーカーが納品サイトの第1版を作り、状態が「運営確認」になります（再読み込み）。
   「この版を顧客確認に回す」で表示される顧客用URL（`http://localhost:3100/review/<token>`）をログインしていないブラウザで開き、
   「この内容で承認する」と内容確認のチェックを付けて「承認を送信する」。
   運営側で「公開を記録する」（AWSへの公開はしない。状態の記録だけ）→ 状態が「納品」になります。

**既知の制約**：生成はモックの固定応答なので、どの企業のデモサイト・納品サイトも架空の「株式会社あおば工務店」の内容になります。
診断の収集データも全社共通の架空サイトです。

## 一時的に外部から見せる（トンネル）

ユーザーの判断（2026-10-14）で、このマシンで動かすデモを一時的なトンネル（例：Cloudflare の Quick Tunnel）で外部から見られるようにできる。
**デモのDBに実在企業の名称・評価点・非公式の改善デモが入っている場合、それも見えるようになる。** ログインなしで見られる画面は増やさない
（企業一覧・詳細はログイン必須、提案デモ・顧客確認は期限付きの共有リンクだけ）。アカウントとリンクは見せる相手にだけ渡す。

1. web（3100）とプレビュー（3200）のそれぞれにトンネルを張り、2つの公開URL（https）を控える。
2. web を本番ビルドにしてから、公開URLを渡してデモを起動する（開発サーバーはエラー表示でソースが見えるため、外部には出さない）。

```sh
pnpm --filter @siteoffer/web build
WEB_BASE_URL=<webの公開URL> \
DEMO_PUBLIC_PREVIEW_URL=<プレビューの公開URL> \
PREVIEW_FRAME_ANCESTORS="'self' <webの公開URL>" \
DEMO_WEB_PROD=1 pnpm demo
```

- `DEMO_PUBLIC_PREVIEW_URL`：営業の共有リンクと、webに埋め込むプレビューのURL。`WEB_BASE_URL`：顧客確認URL。
  `PREVIEW_FRAME_ANCESTORS`：プレビューを埋め込んでよいオリジン（スペース区切り）。
- やめるときはトンネルを止める（デモは Ctrl+C）。Quick Tunnel のURLは張り直すたびに変わり、古い共有リンクも使えなくなる。
- 固定のURLで常時公開し、`origin/main` の更新を自動で反映する場合は [deploy/cloudflare/README.md](../deploy/cloudflare/README.md)（名前付きトンネル・公開専用クローン）を使う。
- 公開前に認証・接続元制限・公開期限と停止方法を確認する。デモ用パスワードは乱数だが、公開中はログを見て、不要になったらすぐ止める。

### 共有リンクをもう一度表示する

新しく発行した提案リンクは、発行した営業担当が「自分が発行したリンク」の「リンクを表示」から同じURLを取り出せます。発行時の通信切断は「同じ発行を再確認」で復旧します。再表示・再試行では期限を延長しません。画面やログにURLを永続保存する仕組みにはしていません。

デモ用の復旧鍵は `.data/demo/share-token-key` に初回だけ生成し、通常の停止・起動では保持します。DBと一緒に安全に保管し、Gitやログへ出さないでください。デモをリセットするとDBと鍵を一緒に作り直します。初期方式で発行済みのリンクは再表示できないため、画面で区別します。

通常のローカル開発では `pnpm dev:setup` が `.env` の `SITEOFFER_SHARE_TOKEN_KEY` を初期化します。全Webインスタンスには同じ32バイトのbase64url鍵を設定してください。プレビュー・ワーカーには不要です。鍵の欠落・破損・別の鍵への変更時は再表示を拒否し、代わりのリンクを勝手に発行しません。すでに配布したURLの検証はDBのハッシュで継続します。鍵を更新する場合は、以前のリンクの再表示が必要な期間の保管・移行を事前に計画してください。


## 暗号化バックアップと復元確認

通常の `pnpm demo` を起動した運営アカウントで「管理 → バックアップ」を開きます。新しい受付を追加する前から稼働しているデモは、作業中のジョブがないことを確認して正常に再起動してください。受付の設定がない環境では利用できない旨を表示します。

- 保存用パスフレーズを2回入力すると、DB、DBから参照する生成サイト・診断成果物、共有リンクの復旧鍵、デモ用アカウント記録を1つの暗号化ファイルに保存します。`.env`、APIキー、無関係なホスト上のファイルは対象外です。
- パスフレーズは12〜1024文字で、アプリには保存しません。忘れた場合は復元できません。暗号化ファイルとは別の安全な場所に保管してください。HTTPでパスフレーズを入力するのはローカル端末だけとし、外部接続にはHTTPSを使ってください。
- DBのスナップショット取得中だけ、ほかのDB処理が一時的に待機します。成果物の照合・暗号化・復元確認はDBの専有を解放してから行います。別のバックアップは同時実行しません。保存後は別フォルダーでDBを実際に開き、全テーブルの件数とファイルのSHA-256を照合してから「復元確認済み」にします。確認用の復元データは照合後に削除します。
- 処理中はDB待ち・DB取得・成果物照合・暗号化・復元確認の段階と確認ファイル数を表示します。画面を開き直しても稼働中の受付に状況を問い合わせます。処理中は新しい保存・再検証を無効にし、通信失敗を完了と扱いません。状況の読み取りはデータを変更しません。
- 「復元未確認」は完了した暗号化ファイルがあっても復元確認が成功していない状態です。ファイルを再検証できます。「保存未完了」は完成ファイルがない状態で、ダウンロード対象になりません。確認済みの容量・更新日時と変わったファイルも再検証してください。
- ダウンロードは有効な運営ユーザーだけが利用でき、分割取得に対応します。表示するSHA-256は復元確認時に読み取った暗号化ファイルの値です。保管後の破損を常時検出するものではありません。
- 通常の保存先は `.data/backups/backup-<UUID>/backup.sob` です。`demo:reset` の削除対象には含めません。同じディスク上のコピーだけでは端末故障に備えられないため、暗号化ファイルを別の保存先にも保管してください。

端末からの作成もできます。対話端末ではパスフレーズを伏せて入力します。パスフレーズをコマンド引数に書かないでください。

```sh
pnpm demo:backup
pnpm demo:restore <保存した.sobファイル>
```

復元は `.data/restores/backup-<UUID>` の新規フォルダーに行います。パスフレーズとファイルの認証、DBの版、テーブルの件数、成果物の参照を確認し、現在のデータには上書きしません。参照先は復元フォルダー内へ付け替えます。復元デモのバックアップも通常のデータとは別の保存先に分けます。

```sh
pnpm demo:restored <完了した復元フォルダー>
```

通常のデモが動いている場合は同じポートを使用できません。通常のデモを正常停止するか、`DEMO_DB_PORT`・`DEMO_WEB_PORT`・`DEMO_PREVIEW_PORT` に別の未使用ポートを指定してください。復元デモはモックで動作し、画面上に復元した確認用データであることを表示します。元の環境への切替やAPI接続、DNS設定は自動では行いません。

```sh
pnpm demo:stop
```

Web・プレビュー・ワーカーの後にDBを正常停止します。停止後もDB・バックアップは残ります。強制終了などで利用記録が残ったときだけ、対象プロセスが終了したことを確認して `pnpm demo:unlock` を実行します。稼働中の利用記録は解除できません。復元デモに対する端末の停止・解除では、起動したときと同じ `DEMO_RESTORE_DIR` を設定してください。

現在の保存形式はPGlite用で、保存時と同じPGliteの版が必要です。新しい版への移行は別途検証してください。通常のPostgreSQL・AWSのバックアップ、自動の定期保存・世代削除、端末外への自動転送、本番環境の復旧訓練を完了したものではありません。非対話実行向けの `SITEOFFER_BACKUP_PASSPHRASE` は利用できますが、値をログ・履歴・Gitに保存しないよう管理が必要です。デモ起動時にはこの値を子プロセスへ引き継ぎません。

## バックアップの保管・容量

運営の「バックアップ」から「保護指定・保存期間の条件で整理・容量の確認」を開きます。対象は、その実行環境のバックアップ保存先にあるコピーです。

1. 保管中・退避先で使っているファイル容量と、保存先ディスクの空きを確認します。長く残す保存には「整理から保護」を指定できます。
2. 新しい保存を残す件数と経過日数で「整理候補を確認」します。初期表示の3件・30日は提案値です。0日は日付を絞らず、件数・保護指定・直近の復元確認済みを残します。この画面から自動削除は設定されません。
3. 対象のフルパス・ファイル数・容量と残す条件を確認し、確認欄を選んで退避します。最大100件ずつ、記録量に応じて分けて進めます。退避先も同じディスクを使うため、この時点で空き容量は増えません。
4. 退避した操作の「内訳と操作を確認」から、元の一覧へ戻すか、完全削除へ進めます。同じ名前の保存があれば上書きせず停止します。
5. 完全削除では、残す復元確認済みの保存とそのパスフレーズを指定し、対象と影響を確認します。残す保存を別フォルダーで実際に復元して照合した後、退避先の記録済みファイルだけを削除します。完全削除を開始すると元には戻せません。

プレビュー後の変更、リンク・共有ファイル、記録外のファイル、読み取れない保管は整理を止めます。未確認の部分を空扱いにせず、画面に案内します。記録量に上限があり、極端に大きな記録は個別の運用確認が必要です。空き容量は同じディスクのほかの処理でも変化するため、削除したファイル容量とディスク空きの増減は別の値です。

途中で止まった場合は保管一覧を更新してください。移動・復元・削除の途中経過を記録し、元と退避先の状態を確認して再開します。完全削除を開始した操作は、残す保存をもう一度復元確認してから残りを削除します。操作記録はファイルの完全削除後も残ります。通常のバックアップ保存・再検証と保管操作を同時には実行せず、利用停止や役割変更も操作中に再確認します。

## 任意の実サイト候補検索

通常・復元デモでは実サイト検索を無効にし、環境にある `TAVILY_API_KEY` も子プロセスへ渡しません。

検索APIの製品の本採用は未決です。Tavilyの接続部は利用できますが、契約と利用条件を確認してから有効にしてください。`.env` に `SITEOFFER_SEARCH_PROVIDER=tavily` と `TAVILY_API_KEY` を設定し、国税庁の実収集モード（`start-discovery.cmd`）または通常の実収集ワーカーを正常に起動します。実収集で検索設定がなければ法人情報の収集までを行い、キーがあるだけでは実検索を有効にしません。キーをGit、画面、操作メモへ書かないでください。

`SITEOFFER_SEARCH_MAX_PER_RUN` は1試行の検索回数上限で、既定50、1〜1000です。再試行は別枠になり、日次・月次の課金上限ではありません。画面の「設定済み」は接続成功や残高を保証しません。認証・利用上限に達すると追加の検索を止め、企業情報と理由を残します。

検索候補は企業詳細の「公式サイトの候補URLと確認根拠を追加」で確認できます。URLと検索の出典を入力補助できますが、会社名・所在地などを実ページで確認し、根拠を記録してから候補を保存します。公式サイトの確定と診断依頼はそれぞれ別操作です。第三者サイトや別企業と判定されたURLを自動で公式サイトへ昇格させません。
